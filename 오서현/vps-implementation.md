# VPS (Visual Positioning System)

> 카메라 영상만으로 실내 위치·방향을 추정하는 VPS의 원리와 구현 파이프라인 정리.

---

## 1. VPS란

**사전에 촬영한 이미지로 공간의 3D 포인트맵을 만들어두고, 사용자가 찍은 사진을 그 맵에 매칭시켜 카메라의 위치와 방향(6DoF 포즈)을 역산하는 측위 방식.**

| 항목 | 내용 |
| --- | --- |
| 원리 | 사전 촬영 이미지로 3D 포인트맵 구축(SfM) → 쿼리 이미지 특징점 매칭 → 6DoF 포즈 추정 |
| 기대 정확도 | 1m 이내 ~ 수 m |
| 인프라 설치 | **불필요** (촬영만) |
| 난이도 | 높음 |

GPS가 닿지 않는 실내에서, 비콘·UWB 같은 **하드웨어를 설치하지 않고** 측위할 수 있다는 것이 가장 큰 장점이다. 필요한 건 카메라와 사전 촬영 데이터뿐이다.

### 6DoF (Six Degrees of Freedom)
카메라의 자유도 6개 = **위치 3개(x, y, z) + 회전 3개(roll, pitch, yaw)**.

실내 내비게이션 관점에서 실제로 쓰이는 값은 4개다:
- `x, y` — 평면 위치
- `z` — 층 판정 (맵을 층 통합 좌표계로 만들면 z값이 곧 층이 된다)
- `yaw` — 어느 방향을 보고 있는가

**yaw가 없으면 지도를 띄워도 쓸 수 없다.** "내가 어디 있는지"보다 "내가 어느 쪽을 보고 있는지"가 길안내의 핵심이기 때문이다.

---

## 2. VPS는 "이미지 학습"이 아니다

가장 흔한 오해.

| 오해 | 실제 |
| --- | --- |
| 사진 수천 장으로 "여기는 3번 출구"라는 분류 모델을 학습시킨다 | ❌ 아님 |
| 사진에서 **특징점을 추출**해 3D 기하 구조를 복원하고, **기하학적으로 매칭**해 포즈를 계산한다 | ✅ 이게 VPS |

학습된 모델(NetVLAD, SuperPoint 등)을 쓰긴 하지만, 그건 **"특징점을 잘 뽑는 범용 사전학습 모델"**이지 특정 공간을 학습한 모델이 아니다.

이 차이가 만드는 실질적 결과:
- **데이터 라벨링이 필요 없다** — 촬영만 하면 된다
- 공간이 바뀌어도 **재학습이 아니라 재촬영**이다
- 새 공간을 추가하는 비용이 "모델 훈련"이 아니라 "맵 구축"이다

## 3. 파이프라인

VPS는 **오프라인(사전 구축)**과 **온라인(런타임)** 두 단계로 나뉜다.

### 3.1 오프라인 — 맵 구축

```
[공간 촬영 (동영상)]
        ↓  프레임 추출
[이미지 수천 장]
        ↓  COLMAP (SfM: Structure-from-Motion)
[3D 포인트클라우드 + 각 이미지의 카메라 포즈]
        ↓  hloc
[측위 DB: 글로벌 디스크립터 + 로컬 특징점 인덱스]
```

#### ① 데이터 수집
- 스마트폰 핸드헬드 촬영으로 충분 (LiDAR 불필요)
- 통로당 왕복 2~3회, 다양한 각도
- 사람이 찍혔다면 얼굴 블러 처리 (초상권)

#### ② 3D 재구성 (SfM) — COLMAP
**Structure-from-Motion**: 여러 장의 2D 사진에서 공통으로 보이는 특징점을 찾아 **삼각측량**으로 3D 좌표를 복원하는 기법.

- 입력: 이미지 여러 장
- 출력: 3D 포인트클라우드 + **각 사진이 어디서 찍혔는지(카메라 포즈)** + 카메라 내부 파라미터(초점거리, 왜곡계수 등)
- 핵심: 3D 구조와 카메라 위치를 **동시에** 푼다. 둘 다 모르는 상태에서 사진 간의 대응 관계만으로 역산하는 것
- **GPU 필요.** 이미지 수천 장 규모에서 CPU만으로는 현실적이지 않다

#### ③ 측위 DB 구축 — hloc (Hierarchical-Localization)
**"Hierarchical" = 계층적**, 즉 **거칠게 좁히고 → 정밀하게 맞추는** 2단계 구조다.

이 구조를 쓰는 이유: 수천 장 전부와 정밀 매칭하면 너무 느리다. 먼저 후보를 몇 장으로 줄인 뒤 그것만 정밀하게 본다.

| 단계 | 하는 일 | 대표 모델 |
| --- | --- | --- |
| **이미지 검색** (coarse) | 쿼리 사진과 비슷한 후보 지점 top-k개를 DB에서 빠르게 찾음 | **NetVLAD** — 사진 1장 → 벡터 1개(글로벌 디스크립터). 벡터 유사도 검색이라 빠름 |
| **특징점 추출** (fine) | 사진 안의 코너·모서리 같은 고유 지점과 그 기술자(descriptor)를 뽑음 | **SuperPoint** |
| **특징점 매칭** | 쿼리와 후보 이미지의 특징점을 짝지음 | **LightGlue** / SuperGlue |

> **LightGlue vs SuperGlue**: LightGlue는 SuperGlue의 경량화 버전으로, 매칭 난이도에 따라 연산을 조기 종료(adaptive depth)해 속도를 끌어올린다. GPU 확보가 불확실하거나 CPU 폴백이 필요한 환경에서 유리하다.

#### ④ 경로 그래프 (VPS와 별개 작업)
VPS는 "내가 어디 있나"까지만 답한다. "거기서 목적지까지 어떻게 가나"는 별도의 문제다.

- 2D 도면 기반 노드-엣지 그래프
- 노드 = 갈림길, 계단, 엘리베이터, 출구 / 엣지 = 통로
- 경로 탐색은 다익스트라/A*로 충분 (그래프 규모가 작음)

### 3.2 온라인 — 런타임 측위

```
[카메라 프레임 2~3장]
        ↓
[NetVLAD → top-k 후보 지점 검색]
        ↓
[SuperPoint + LightGlue → 특징점 매칭]
        ↓
[PnP + RANSAC → 포즈 계산]
        ↓
[{x, y, z, yaw, confidence}]
```

#### PnP (Perspective-n-Point)
**"3D 점이 2D 사진의 어디에 찍혔는지"를 n쌍 알면 카메라의 위치와 자세를 역산할 수 있다**는 기하학 문제.
매칭으로 얻은 3D-2D 대응쌍을 PnP에 넣으면 카메라 포즈가 나온다. 최소 3~4쌍이면 수학적으로 풀리지만, 실제로는 오차 때문에 훨씬 많이 쓴다.

#### RANSAC (Random Sample Consensus)
특징점 매칭에는 **반드시 오답(outlier)이 섞인다.** 오답이 하나만 섞여도 PnP 결과가 크게 틀어진다.

RANSAC은 이렇게 동작한다:
1. 매칭 중 무작위로 소수만 뽑아 포즈를 계산
2. 그 포즈가 **나머지 매칭 중 몇 개와 일치하는지** 센다
3. 1~2를 여러 번 반복 → **가장 많은 매칭이 동의한 답**을 채택

여기서 동의한 매칭 개수 = **인라이어(inlier) 수**.

> **인라이어 수가 곧 신뢰도다.**
> 임계값(예: 15개) 미만이면 "측위 실패"로 판정하고 사용자에게 재시도를 요청하는 식으로 쓴다.
> VPS 구현에서 이 임계값 튜닝이 실무의 상당 부분을 차지한다.

## 4. 동적 객체(사람) 처리

### 4.1 왜 사람이 문제인가

SfM은 **"여러 사진에서 같은 지점이 같은 자리에 있다"**를 전제로 3D를 복원한다.
사람은 움직이므로 이 전제를 깬다.

두 가지 방식으로 망가진다:
1. **재구성 오염** — 잘못된 3D 점이 생기거나, 재구성 자체가 실패
2. **매칭 실패** — 사람의 옷·가방에서 뽑힌 특징점이 맵에 박히면, 나중에 그 사람이 없을 때 그 지점이 매칭되지 않음

### 4.2 대응 3종

| 시점 | 방법 | 비용 | 효과 |
| --- | --- | --- | --- |
| **촬영 시** | 한산한 시간대에 촬영 | 무료 | 가장 크다 |
| **맵 구축 시** | 사람 영역 세그멘테이션 → 마스킹 후 SfM | 중 | 남은 행인 제거 |
| **쿼리 시** | 사용자 사진에서도 동일하게 사람 마스킹 | 중 | 유동인구 많을 때 매칭률 방어 |

**촬영 시간대 조절이 압도적으로 싸다.** 세그멘테이션은 "그래도 남은 사람"에 대한 대응이지, 촬영 계획을 대체하지 못한다.

### 4.3 사람만이 아니다 — 변화하는 영역 전반

VPS의 실서비스 관점 최대 약점은 **"공간이 바뀌면 맵이 낡는다"**는 것이다. 리모델링, 상점 교체, 광고 교체마다 재촬영이 필요하면 유지비용이 서비스를 죽인다.

**대응: 특징점을 안 바뀌는 것 위주로 유도한다.**

| | 대상 | 이유 |
| --- | --- | --- |
| ✅ **유지** | 천장 구조, 기둥, 계단, 게이트, 벽 모서리 | 수년 단위로 안 바뀜 |
| ❌ **마스킹** | 사람, 광고판, 상점 간판, 전광판 | 수주~수개월 단위로 바뀜 |

이러면 변화 내성이 올라간다. 다만 **"유지비용이 0"이 되는 건 아니다.** 상용 VPS도 부분 재스캔·크라우드소싱 업데이트로 운영한다. 정직한 주장은 "비용이 없다"가 아니라 **"부분 갱신 가능한 구조"**다.

### 4.4 주의: 과하게 지우면 역효과

지하 공간·복도는 이미 특징점이 부족한 환경이다 (균일한 벽면, 반복 패턴, 텍스처 없는 면).
사람·광고판까지 전부 지우면 **남는 특징점이 너무 적어 매칭 자체가 실패**할 수 있다.

마스킹은 무조건 이득이 아니라 **트레이드오프**다:
- 마스킹 ↑ → 변화 내성 ↑, 하지만 특징점 밀도 ↓
- 마스킹 ↓ → 특징점 풍부, 하지만 시간이 지나면 매칭률 붕괴

→ **적정선은 공간마다 다르므로 실측으로 정해야 한다.** 마스킹 유/무를 둘 다 돌려서 성공률을 비교하는 게 유일하게 확실한 방법.

## 5. VPS의 대표적 실패 케이스: Perceptual Aliasing

**전혀 다른 두 지점이 시각적으로 거의 똑같아서, 이미지 검색 단계(NetVLAD)가 엉뚱한 후보를 top-1으로 올리는 현상.**

실내에서 특히 심하다. 지하철 통로, 주차장, 사무실 복도처럼 **설계상 반복되는 구조**를 가진 공간이 최악이다. 야외는 건물·간판·지형이 다 달라서 상대적으로 덜하다.

**대응:**

| 방법 | 원리 |
| --- | --- |
| **시퀀스 측위** | 단일 프레임이 아니라 수 초 동안의 여러 뷰를 사용 → 이동하며 얻은 뷰들이 후보를 좁힘 |
| **사전 정보(prior) 활용** | 직전 위치를 알면, 걸어서 도달 불가능한 후보는 배제. PDR·GPS 힌트를 넣으면 검색 공간이 줄어 속도도 빨라짐 |
| **인라이어 임계값** | aliasing으로 잘못 매칭되면 인라이어가 적게 나오는 경향 → 실패로 판정하고 재시도 |
| **폴백 UX** | "몇 걸음 걸으며 주변을 비춰주세요" — 실패를 숨기지 말고 사용자 행동으로 해결 |

> **테스트 환경 선정에 직결되는 함정**
> aliasing이 없는 공간(예: 특징이 뚜렷한 사무실)에서 검증하면 성공률이 높게 나온다.
> 하지만 그 숫자는 반복 구조를 가진 실제 대상 공간의 성능을 전혀 예측하지 못한다.
> **검증은 리스크가 재현되는 환경에서 해야 의미가 있다.**

## 6. 온디바이스 vs 서버 측위

| | 온디바이스 | 서버 |
| --- | --- | --- |
| 연산 | 폰에서 특징점 추출·매칭 | 서버가 처리, 폰은 이미지만 전송 |
| 장점 | 오프라인 동작, 왕복 지연 없음 | 저사양 기기·웹 환경 대응, 맵 갱신 즉시 반영 |
| 단점 | 저사양 기기에서 버거움, **웹에서는 사실상 불가** | 네트워크 필요, 왕복 지연 |
| 맵 배포 | 앱에 내장하거나 다운로드 | 서버에만 있음 |

**웹 기반이면 서버 측위가 사실상 유일한 선택.** 브라우저에서 SuperPoint 추론을 돌리는 건 현실적이지 않다.

### 전송 방식
측위 쿼리는 **초당 몇 번, 프레임 2~3장**이면 충분하다. 실시간 연속 스트림이 아니다.
→ `canvas.toBlob()`으로 프레임을 캡처해 **multipart POST**로 보내는 것으로 충분하다. 영상 스트리밍 프로토콜이 필요한 작업이 아니다.

측위 사이의 빈 구간은 **PDR(보행자 추측항법)**로 메우고, 주기적으로 VPS 재측위로 누적 오차를 리셋하는 하이브리드가 일반적이다.

## 7. 정리 — VPS의 성립 조건

| 조건 | 내용 |
| --- | --- |
| **텍스처가 있어야 한다** | 특징점이 안 뽑히는 백색 벽면·유리면은 측위 불가 |
| **구조가 구별되어야 한다** | 반복 구조 = perceptual aliasing |
| **조명이 안정적이어야 한다** | 실내는 오히려 야외보다 유리 (조명이 일정) |
| **동적 객체가 적어야 한다** | 촬영 시점 기준. 쿼리 시점은 마스킹·폴백으로 방어 |
| **GPU가 있어야 한다** | 최소한 맵 구축 단계에서는 |

**정확도는 "cm 단위"가 아니라 용도에 맞춰 정의해야 한다.**
길안내라면 "갈림길에서 어느 방향인지 판단 가능"하면 성립하고, 이는 대체로 **오차 2~5m + 방향 정확도** 수준이다. 직선 구간 한가운데서는 정밀 위치가 애초에 필요 없다.
