## 1. 실내 위치 파악을 위해 3D 지도가 필요한 이유

### 1.1 우리가 해결하려는 기술 문제

우리 서비스에서 사용자는 지하철역 내부에서 스마트폰 카메라를 켜고 주변을 비춘다. 시스템은 카메라에 들어온 영상을 분석해 다음 정보를 추정해야 한다.

* 사용자가 역사 내부의 어느 지점에 있는지
* 어느 층에 있는지
* 어느 방향을 바라보고 있는지
* 현재 위치에서 목적지까지 어느 방향으로 이동해야 하는지

GPS가 잘 작동하지 않는 실내에서는 카메라 영상을 이용해 위치를 추정하는 **Visual Localization, 즉 시각적 위치 추정 기술**이 필요하다.

이때 시스템이 단순히 현재 사진과 기존 사진을 비교하기만 하면 다음 정도밖에 알 수 없다.

> “현재 사진은 사전에 촬영한 137번 사진과 가장 비슷하다.”

이는 대략적인 장소 분류에는 사용할 수 있지만, 사용자의 정확한 위치와 방향을 계산하기에는 부족하다.

따라서 사전에 역사 내부를 여러 위치와 각도에서 촬영하고, 이미지 속 고정된 특징점들의 3차원 좌표를 복원한 **측위용 3D 지도**가 필요하다.

---

### 1.2 여기서 말하는 3D 지도란 무엇인가

우리가 구축하려는 3D 지도는 게임이나 메타버스처럼 벽·바닥·사물을 정교하게 표현한 3D 모델이 아니다.

측위에 필요한 데이터만 저장한 **희소 3D 포인트 맵(Sparse 3D Point Map)**이다.

예를 들어 역사 내부의 다음 요소들이 3D 특징점이 될 수 있다.

* 천장 모서리
* 기둥의 경계
* 벽면 타일의 모서리
* 고정 안내판의 글자와 테두리
* 출입구와 문틀
* 계단과 난간 구조
* 개찰구와 엘리베이터 입구

이러한 특징점들은 다음과 같은 형태로 저장된다.

```text
3D 특징점 A = (x: 12.4, y: 3.2, z: 1.8)
3D 특징점 B = (x: 13.7, y: 4.1, z: 2.3)
3D 특징점 C = (x: 15.2, y: 2.8, z: 1.5)
```

각 특징점에는 이 점이 어떤 기준 이미지에서 관찰됐는지도 함께 저장된다.

```text
특징점 A
 ├─ 기준 이미지 12번에서 관찰
 ├─ 기준 이미지 18번에서 관찰
 └─ 기준 이미지 23번에서 관찰
```

여러 이미지에서 동일한 특징점을 찾으면 삼각측량을 통해 해당 점의 3차원 위치와 각 이미지가 촬영된 카메라 위치를 계산할 수 있다. 이러한 과정을 **SfM(Structure from Motion)**이라고 한다.

COLMAP은 여러 이미지에서 특징점을 추출하고, 이미지 간 대응점을 찾은 뒤, 카메라 위치와 희소 3D 구조를 복원하는 SfM 파이프라인을 제공한다.

---

### 1.3 3D 지도를 이용해 현재 위치를 찾는 원리

사용자가 새롭게 촬영한 카메라 이미지에서 특징점을 추출한 뒤, 사전에 만든 3D 지도와 비교한다.

예를 들어 현재 이미지에서 다음과 같은 점들이 발견됐다고 가정한다.

```text
현재 이미지의 점 (u1, v1)
↔ 3D 지도상의 점 (x1, y1, z1)

현재 이미지의 점 (u2, v2)
↔ 3D 지도상의 점 (x2, y2, z2)

현재 이미지의 점 (u3, v3)
↔ 3D 지도상의 점 (x3, y3, z3)
```

즉, 현재 카메라 화면의 2차원 점과 실제 공간의 3차원 점 사이에 대응 관계가 만들어진다.

이 대응 관계를 이용해 카메라의 위치와 회전을 계산하는 문제가 **PnP(Perspective-n-Point)**다.

PnP의 입력은 다음과 같다.

* 실제 공간에 존재하는 3D 특징점 좌표
* 현재 이미지에서 관찰된 2D 특징점 좌표
* 스마트폰 카메라의 내부 파라미터

출력은 다음과 같다.

* 카메라의 위치 `x, y, z`
* 카메라의 회전 및 방향

OpenCV의 `solvePnP` 계열 함수는 3D 점과 대응하는 2D 이미지 점을 이용해 회전 벡터와 이동 벡터를 계산한다. `solvePnPRansac`을 사용하면 잘못 매칭된 특징점을 제외하면서 포즈를 추정할 수 있다.

최종적으로 시스템은 다음과 같은 값을 얻을 수 있다.

```json
{
  "position": {
    "x": 12.42,
    "y": 8.17,
    "z": 1.63
  },
  "orientation": {
    "yaw": 91.4,
    "pitch": -2.8,
    "roll": 0.7
  }
}
```

이 값으로 사용자의 위치를 실내 지도 위에 표시하고, 사용자가 바라보는 방향에 맞춰 길을 안내할 수 있다.

## 2. 전체 기술 구조

우리 서비스의 Visual Localization 파이프라인은 다음과 같이 구성한다.

```text
[오프라인 지도 구축]

역사 내부 영상 촬영
        ↓
영상에서 프레임 추출
        ↓
이미지 특징점 추출
        ↓
이미지 간 특징점 매칭
        ↓
SfM으로 카메라 위치와 3D 특징점 복원
        ↓
측위용 희소 3D 지도 구축


[온라인 사용자 측위]

사용자 카메라 이미지 입력
        ↓
비슷한 기준 이미지 검색
        ↓
기준 이미지와 현재 이미지 특징점 매칭
        ↓
2D 이미지 점과 3D 지도 점 연결
        ↓
PnP + RANSAC으로 카메라 포즈 계산
        ↓
지도 좌표로 변환
        ↓
현재 위치와 진행 방향 표시
```

이를 구현하기 위해 사용하는 핵심 기술은 다음과 같다.

| 기술                      | 역할                                         |
| ----------------------- | ------------------------------------------ |
| COLMAP                  | 촬영 이미지로 카메라 위치와 3D 특징점 복원                  |
| SfM                     | 여러 이미지에서 공간의 3D 구조를 계산하는 원리                |
| hloc                    | 이미지 검색·특징점 매칭·Visual Localization 전체 파이프라인 |
| NetVLAD 또는 이미지 검색 모델    | 현재 이미지와 비슷한 장소의 기준 이미지 검색                  |
| SuperPoint              | 이미지에서 위치 추정에 사용할 특징점과 디스크립터 추출             |
| LightGlue               | 현재 이미지와 기준 이미지의 특징점을 서로 연결                 |
| PyCOLMAP                | Python에서 COLMAP 모델과 포즈 추정 기능 사용            |
| PnP                     | 2D–3D 대응점을 이용해 카메라 위치와 방향 계산               |
| RANSAC                  | 잘못 연결된 특징점을 제거하고 안정적인 포즈 계산                |
| FastAPI                 | 측위 기능을 API로 제공하는 Python 서버                 |
| OpenCV                  | 이미지 전처리, 카메라 파라미터 처리, PnP 계산               |
| FAISS 또는 hloc retrieval | 기준 이미지의 글로벌 디스크립터 검색                       |
| SVG 또는 Canvas           | 추정 위치를 2D 실내 지도에 표시                        |

## 3. COLMAP

### 3.1 COLMAP의 역할

COLMAP은 여러 장의 사진을 이용해 다음 두 가지를 복원하는 오픈소스 도구다.

1. 사진이 촬영된 카메라의 위치와 방향
2. 사진 속 공간의 희소 3D 특징점

우리 프로젝트에서는 역사 내부를 촬영한 영상에서 프레임을 추출한 뒤 COLMAP에 넣는다.

```text
역사 촬영 이미지
        ↓
특징점 추출
        ↓
이미지 간 특징점 연결
        ↓
카메라 포즈 복원
        ↓
희소 3D 포인트 생성
```

COLMAP의 기본 SfM 과정은 특징점 추출, 이미지 간 대응점 검색, 기하 검증, 점진적인 3D 재구성으로 구성된다.

### 3.2 COLMAP의 결과물

COLMAP이 생성하는 핵심 결과는 다음과 같다.

```text
sparse/0/
├─ cameras.bin
├─ images.bin
└─ points3D.bin
```

* `cameras.bin`: 카메라 모델과 내부 파라미터
* `images.bin`: 기준 이미지별 카메라 위치와 방향
* `points3D.bin`: 공간에 복원된 희소 3D 특징점

COLMAP은 텍스트 형식으로도 `cameras.txt`, `images.txt`, `points3D.txt` 등의 재구성 결과를 출력할 수 있다.

### 3.3 왜 Dense 3D 모델이 필요하지 않은가

COLMAP은 필요하면 Multi-View Stereo를 이용해 촘촘한 포인트클라우드나 표면 모델까지 만들 수 있다.

하지만 우리 서비스의 목적은 3D 모델을 사용자에게 보여주는 것이 아니라, 카메라의 위치를 계산하는 것이다.

따라서 다음 결과만 있으면 된다.

```text
기준 이미지의 카메라 위치
+
각 이미지에서 관찰된 3D 특징점
```

즉, MVP에서는 다음 작업은 하지 않아도 된다.

* 3D 메시 생성
* 텍스처 매핑
* 실사형 3D 역사 모델
* NeRF
* Gaussian Splatting
* Unity용 3D 모델 제작

이 작업들은 시각화에는 도움이 되지만 Visual Localization의 핵심 구현에는 필요하지 않으며, 프로젝트 기간을 크게 소모할 가능성이 높다.

## 4. hloc

### 4.1 hloc의 역할

hloc는 ETH Zurich Computer Vision and Geometry Group에서 공개한 Visual Localization 도구다.

hloc는 다음 기능을 하나의 파이프라인으로 연결한다.

* 글로벌 이미지 검색
* 로컬 특징점 추출
* 이미지 간 특징점 매칭
* SfM 모델 생성
* 쿼리 카메라의 6DoF 위치 추정

공식 저장소는 hloc를 이미지 검색과 특징점 매칭을 활용하는 6DoF Visual Localization 도구로 설명한다.

우리 프로젝트에서는 직접 Visual Localization 알고리즘 전체를 처음부터 구현하기보다 hloc를 기반으로 구성하는 것이 현실적이다.

### 4.2 hloc를 사용하는 이유

COLMAP만으로도 SfM 지도는 만들 수 있지만, 사용자가 새로 촬영한 사진의 위치를 찾는 온라인 파이프라인은 별도로 구성해야 한다.

hloc는 이 과정을 다음과 같이 제공한다.

```text
현재 이미지
    ↓
기준 이미지 검색
    ↓
특징점 추출
    ↓
특징점 매칭
    ↓
2D–3D 대응점 생성
    ↓
카메라 위치 추정
```

따라서 역할을 구분하면 다음과 같다.

```text
COLMAP
= 3D 지도 생성 도구

hloc
= 생성된 3D 지도에서 현재 카메라 위치를 찾는 전체 프레임워크
```

실제로는 hloc 내부에서도 PyCOLMAP을 사용해 SfM 모델 생성과 포즈 추정을 수행할 수 있으므로, 최종 구현에서는 hloc 중심으로 파이프라인을 구성하는 편이 더 단순하다.

## 5. 글로벌 이미지 검색

### 5.1 필요한 이유

역사 기준 이미지가 2,000장 있다고 가정하면 현재 이미지와 2,000장을 모두 정밀하게 특징점 매칭하는 것은 비효율적이다.

먼저 현재 이미지와 시각적으로 유사한 장소의 사진을 빠르게 검색한다.

```text
현재 이미지
        ↓
이미지 전체를 대표하는 벡터 추출
        ↓
기준 이미지 2,000장과 유사도 비교
        ↓
가장 비슷한 10~20장만 선택
```

이때 사용하는 이미지 전체의 특징 벡터를 **글로벌 디스크립터**라고 한다.

예를 들어 다음과 같은 후보가 선택될 수 있다.

```text
1위: B1_엘리베이터_032.jpg
2위: B1_엘리베이터_036.jpg
3위: B1_통로_041.jpg
```

이 단계에서는 정확한 위치를 결정하는 것이 아니라, 정밀 매칭을 수행할 후보 범위를 줄인다.

### 5.2 적용 기술

초기에는 hloc에서 제공하는 retrieval 설정을 그대로 사용하는 것이 안전하다.

후보 기술은 다음과 같다.

* NetVLAD 계열 글로벌 디스크립터
* hloc에서 제공하는 이미지 검색 모델
* FAISS 기반 벡터 검색

MVP에서는 별도의 벡터 데이터베이스를 운영할 필요까지는 없다. 역 한 곳의 기준 이미지가 수백~수천 장 규모라면 hloc의 검색 결과를 파일 기반으로 관리하거나 FAISS 인덱스를 메모리에 올리는 정도로 충분하다.

## 6. SuperPoint

### 6.1 SuperPoint의 역할

SuperPoint는 이미지에서 위치 추정에 사용할 수 있는 로컬 특징점을 찾고, 각 특징점을 설명하는 디스크립터를 생성한다.

예를 들어 이미지에서 다음과 같은 지점을 검출할 수 있다.

* 표지판 모서리
* 타일 경계
* 계단 난간의 교차점
* 기둥의 모서리
* 출입구 프레임

결과는 개념적으로 다음과 같다.

```json
{
  "keypoint": [482.3, 311.8],
  "descriptor": [0.12, -0.31, 0.42, "..."]
}
```

`keypoint`는 이미지에서 특징점의 위치이고, `descriptor`는 다른 이미지에서 같은 점을 찾기 위한 특징 벡터다.

### 6.2 기존 SIFT 대신 SuperPoint를 고려하는 이유

COLMAP 기본 파이프라인에서는 전통적인 SIFT 특징점을 사용할 수 있다.

그러나 실제 역사 환경에서는 다음 문제가 있다.

* 카메라 각도가 크게 변함
* 사용자가 촬영하는 높이가 다름
* 조명과 노출이 달라짐
* 사람이 일부 구조물을 가림
* 반복적인 타일과 기둥이 많음

따라서 프로젝트에서는 다음 두 조합을 모두 비교해야 한다.

```text
기준선
SIFT + COLMAP

주력 후보
SuperPoint + LightGlue + hloc
```

처음부터 SuperPoint 조합이 항상 더 좋다고 확정해서는 안 된다. 여러분이 직접 촬영한 역사 데이터에서 등록 이미지 비율, 매칭 수, 측위 성공률과 속도를 비교해야 한다.

## 7. LightGlue

### 7.1 LightGlue의 역할

LightGlue는 두 이미지에서 추출한 특징점 중 동일한 실제 공간의 점을 서로 연결한다.

```text
현재 이미지의 기둥 모서리
        ↕
기준 이미지의 같은 기둥 모서리
```

LightGlue는 특징점과 디스크립터를 입력받아 대응하는 특징점의 인덱스를 반환하는 로컬 특징점 매처다. 공식 구현은 이미지 쌍의 난이도에 따라 계산량을 조절하는 적응형 구조를 사용한다.

### 7.2 LightGlue를 선택하는 이유

SuperGlue도 유사한 역할을 수행하지만, LightGlue는 계산량과 메모리 사용을 줄이면서 빠른 특징점 매칭을 목표로 설계됐다. 특히 상대적으로 매칭이 쉬운 이미지 쌍에서는 네트워크의 깊이와 처리할 특징점 수를 줄일 수 있다.

따라서 우리 프로젝트의 초기 후보는 다음과 같다.

```text
특징점 추출: SuperPoint
특징점 매칭: LightGlue
```

다만 CPU 환경에서 충분한 속도가 나오는지는 기준 이미지 수, 특징점 개수, 이미지 해상도에 따라 달라지므로 실제 서버에서 측정해야 한다.

## 8. PyCOLMAP

PyCOLMAP은 Python에서 COLMAP의 기능을 사용할 수 있도록 제공되는 인터페이스다.

우리 프로젝트에서는 다음 용도로 사용할 수 있다.

* COLMAP 희소 3D 모델 읽기
* 기준 이미지와 3D 특징점 관계 조회
* 카메라 내부 파라미터 처리
* 쿼리 이미지의 포즈 추정
* SfM 모델 분석
* 이미지 등록 여부 확인

이를 통해 Python FastAPI 서버 내부에서 다음과 같은 흐름을 구성할 수 있다.

```python
query_image = load_image(file)

retrieved_images = retrieve_candidates(query_image)

matches = match_query_to_references(
    query_image,
    retrieved_images
)

pose = estimate_camera_pose(
    matches,
    reconstruction
)
```

직접 COLMAP 바이너리 파일을 파싱하기보다 PyCOLMAP을 사용하는 편이 안전하다.

## 9. PnP와 RANSAC

### 9.1 PnP

PnP는 다음 정보를 이용해 카메라 위치를 구한다.

```text
현재 이미지의 2D 점
+
실제 공간의 3D 점
+
카메라 내부 파라미터
```

예를 들어 현재 이미지에 표시된 안내판 모서리가 3D 지도상의 특정 점과 연결되면, 여러 점의 기하학적 관계를 이용해 카메라가 어디에 있는지 계산한다.

OpenCV의 `solvePnP`는 객체 또는 세계 좌표계의 3D 점을 카메라 좌표계로 변환하는 회전 벡터와 이동 벡터를 반환한다.

### 9.2 RANSAC

특징점 매칭 결과에는 잘못 연결된 점이 반드시 섞인다.

예를 들어 서로 다른 기둥의 모서리가 동일한 점으로 잘못 매칭될 수 있다.

RANSAC은 일부 대응점으로 포즈를 반복 계산한 뒤, 계산 결과와 일관된 점들만 인라이어로 선택한다.

```text
전체 매칭 120개
        ↓
RANSAC 검증
        ↓
정상 대응점 82개
오류 대응점 38개 제거
```

결과적으로 다음 값을 측위 신뢰도에 활용할 수 있다.

* 전체 매칭 수
* RANSAC 인라이어 수
* 인라이어 비율
* 재투영 오차

단순히 위치 좌표만 반환하지 말고 이 값을 함께 반환해야 한다.

## 10. OpenCV

OpenCV는 측위 파이프라인의 보조 도구로 사용한다.

주요 사용 항목은 다음과 같다.

* 이미지 리사이즈
* JPEG 디코딩
* 블러 이미지 탐지
* 카메라 내부 파라미터 처리
* 렌즈 왜곡 보정
* `solvePnP`
* `solvePnPRansac`
* 회전 벡터와 회전 행렬 변환
* 카메라 방향 계산

예를 들어 서버는 최종 포즈를 다음 형태로 변환해야 한다.

```text
rotation vector
        ↓
rotation matrix
        ↓
camera position
        ↓
yaw, pitch, roll
```

주의할 점은 `solvePnP`가 반환하는 이동 벡터가 곧바로 우리가 원하는 세계 좌표계의 카메라 위치와 동일한 표현은 아니라는 것이다. 좌표계 변환을 정확히 이해하지 않으면 위치가 반대로 나오거나 회전 방향이 뒤집힐 수 있다.

## 11. 카메라 내부 파라미터

카메라 포즈를 계산하려면 스마트폰 카메라의 내부 파라미터가 필요하다.

주요 값은 다음과 같다.

```text
fx, fy = 초점거리
cx, cy = 이미지 주점
distortion = 렌즈 왜곡 계수
```

카메라 내부 파라미터는 다음 행렬로 표현된다.

```text
K =
[ fx   0  cx ]
[  0  fy  cy ]
[  0   0   1 ]
```

초기 PoC에서는 같은 스마트폰의 같은 렌즈와 같은 해상도를 사용하는 것이 좋다.

```text
지도 촬영
→ iPhone 기본 1배 렌즈

쿼리 촬영
→ 동일 iPhone 기본 1배 렌즈
```

처음부터 여러 기기를 지원하면 각 기기의 화각, 렌즈 왜곡, 이미지 후처리 차이까지 동시에 해결해야 한다.

따라서 검증 순서는 다음이 현실적이다.

```text
1단계: 동일 기기에서 위치 추정 성공
2단계: 다른 동일 OS 기기 테스트
3단계: Android와 iOS 교차 테스트
```

## 12. FastAPI 측위 서버

AI 측위 로직은 Python 생태계의 라이브러리를 많이 사용하므로 Spring 서버 내부에 직접 구현하는 것보다 별도의 FastAPI 서버로 분리하는 것이 적절하다.

```text
Vue 클라이언트
       ↓
Spring Boot
       ↓
FastAPI 측위 서버
       ↓
hloc / PyCOLMAP / PyTorch / OpenCV
```

또는 개발 초기에는 Spring을 거치지 않고 다음처럼 직접 연결할 수 있다.

```text
Vue 클라이언트
       ↓
FastAPI 측위 서버
```

측위가 성공한 뒤 Spring과 통합하는 편이 문제 원인을 분리하기 쉽다.

예상 API는 다음과 같다.

```http
POST /api/localization
Content-Type: multipart/form-data
```

입력:

```text
image
stationId
floorHint
previousX
previousY
previousHeading
```

응답:

```json
{
  "success": true,
  "pose": {
    "x": 12.42,
    "y": 8.17,
    "z": 1.63,
    "yaw": 91.4
  },
  "confidence": {
    "inlierCount": 82,
    "inlierRatio": 0.68,
    "reprojectionError": 1.42
  }
}
```

## 13. 3D 좌표와 실내 지도 좌표 정합

COLMAP으로 얻은 좌표는 자동으로 실제 역사 평면도 좌표가 되지 않는다.

COLMAP 좌표는 다음 요소가 임의로 정해질 수 있다.

* 원점
* 축 방향
* 회전
* 스케일

예를 들어 COLMAP 측위 결과가 다음과 같더라도

```text
(x, y, z) = (-3.2, 8.4, 1.7)
```

SVG 지도에서는 다음 위치일 수 있다.

```text
(mapX, mapY) = (482, 311)
```

따라서 다음과 같은 기준점을 수작업으로 연결해야 한다.

| 실제 지점    | COLMAP 좌표          | 지도 좌표        |
| -------- | ------------------ | ------------ |
| 엘리베이터 앞  | `(3.1, -8.4, 1.5)` | `(482, 311)` |
| 개찰구 중앙   | `(6.7, -2.1, 1.6)` | `(731, 408)` |
| 2번 출구 계단 | `(12.3, 4.5, 1.4)` | `(910, 225)` |

여러 기준점을 사용해 회전·이동·스케일 변환을 계산한다.

```text
지도 좌표
=
스케일 × 회전 × COLMAP 좌표
+
이동값
```

이 정합 작업이 빠지면 카메라 위치는 계산하더라도 지도 위에 정확하게 표시할 수 없다.

## 16. 기술적으로 가장 중요한 검증 질문

이 프로젝트의 성공 여부는 3D 포인트클라우드가 만들어졌는지가 아니다.

다음 질문에 답할 수 있어야 한다.

> 3D 지도 제작에 사용하지 않은 다른 날의 카메라 이미지를 입력했을 때, 현재 위치와 방향을 정확하게 찾을 수 있는가?

따라서 평가 지표는 다음과 같이 잡아야 한다.

* 올바른 구역을 찾은 비율
* 위치 오차
* 방향 오차
* RANSAC 인라이어 수
* 인라이어 비율
* 재투영 오차
* 측위 응답시간
* 측위 실패를 낮은 신뢰도로 감지한 비율

특히 잘못된 위치를 높은 신뢰도로 반환하는 경우가 가장 위험하다.

위치를 찾지 못하면 사용자가 다시 촬영할 수 있지만, 잘못된 방향을 확신해서 안내하면 서비스 신뢰성이 무너진다.

## 17. 최종 정리

이 서비스에서 3D 지도를 구축하는 이유는 역사 내부를 입체적으로 보여주기 위해서가 아니다.

3D 지도는 사용자의 카메라 이미지에 나타난 2D 특징점을 실제 역사 공간의 3D 특징점과 연결하기 위해 필요하다.

이를 통해 카메라의 위치와 방향을 계산할 수 있다.

핵심 기술 구조는 다음과 같다.

```text
COLMAP / PyCOLMAP
→ 역사 내부의 희소 3D 특징점과 기준 카메라 포즈 생성

hloc
→ 이미지 검색부터 Visual Localization까지 전체 흐름 관리

SuperPoint
→ 이미지 특징점 추출

LightGlue
→ 현재 이미지와 기준 이미지 특징점 매칭

PnP + RANSAC
→ 2D–3D 대응점으로 현재 카메라 위치와 방향 계산

FastAPI
→ 측위 기능을 서버 API로 제공

SVG + Vue
→ 계산된 위치를 실내 지도에 표시
```

따라서 우리 프로젝트의 정확한 기술 목표는 다음과 같다.

> 역사의 실사형 3D 모델을 제작하는 것이 아니라, 사전 촬영 이미지로 희소 3D 특징점 지도를 구축하고, 사용자의 카메라 이미지와 3D 특징점을 매칭해 현재 위치와 방향을 추정하는 Visual Localization 시스템을 구현한다.
